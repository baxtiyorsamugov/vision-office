# GPU/CPU: запуск на разных компьютерах

## Одна команда

В PowerShell из папки проекта, после настройки Docker, моделей и `settings.yaml`:

```powershell
powershell -ExecutionPolicy Bypass -File .\start_vision_office.ps1
```

Скрипт собирает CPU-образы, выбирает кандидатный CUDA-профиль по NVIDIA GPU,
собирает его и проверяет настоящие модели. Для каждой активной камеры запускает
отдельные YOLO и FaceID одновременно, удерживая все модели в памяти. Проверяет
CUDA convolution, NMS, связь PyTorch/NumPy, детектор лица и ArcFace. Тест ограничен
240 секундами, не читает RTSP, не пишет события и не вызывает ERP.

Проверка использует синтетические кадры. Она выявляет проблемы библиотек и
базовой вместимости VRAM, но не заменяет тест плотного потока людей и камер.
При отсутствии/ошибке CUDA в режиме `auto` выполняется CPU-проверка. Если и она
не проходит, запуск прекращается с ошибкой, предыдущая настройка сохраняется.
Уже работающая камера временно останавливается на время проверки; запускайте
скрипт в окно обслуживания. Сборка до проверки выполняется без остановки камер.

Успешный выбор записывается в локальный `docker-compose.override.yml`. Его не
нужно редактировать вручную, хранить в Git или переносить на другой компьютер.
Собственный override скрипт не перезаписывает: сначала требуется его проверка.
База PostgreSQL, ERP-контракты, локальные сотрудники и пороги распознавания не меняются.

## Профили

| Устройство | Кандидат | Библиотеки |
| --- | --- | --- |
| Нет NVIDIA; AMD/Intel; неподдерживаемая/неопределённая CUDA | CPU | torch 2.5.1+cpu, torchvision 0.20.1+cpu, ORT 1.23.2 |
| NVIDIA compute capability 6.x–9.x: Pascal, Turing, Ampere, Ada и др. | cu124 | torch 2.5.1+cu124, torchvision 0.20.1+cu124, ORT GPU 1.23.2 |
| NVIDIA compute capability >= 10: Blackwell и более новые кандидаты | cu128 | torch 2.7.1+cu128, torchvision 0.22.1+cu128, ORT GPU 1.23.2 |

Это кандидаты, не гарантия поддержки будущей карты: окончательный выбор зависит
от реального вычислительного теста. GTX 1050 Ti получает кандидат `cu124`,
RTX 4070 также `cu124`. Наличие имени карты в системе само по себе недостаточно.
Список `sm_*` не используется как строгий фильтр: совместимое ядро может работать
на карте, чей точный `sm_*` отсутствует в списке сборки.

Требования: Linux containers / WSL2 в Docker Desktop, совместимый NVIDIA
Windows-драйвер. CUDA/cuDNN уже поставляются библиотеками внутри образа.
Не устанавливайте Linux display driver в WSL. Первая сборка требует интернета,
нескольких гигабайт загрузок и дополнительного места для CPU/GPU-образов и кэша.

Профили основаны на [официальных сочетаниях PyTorch](https://pytorch.org/get-started/previous-versions/),
[требованиях ONNX Runtime CUDA](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html),
[NVIDIA WSL](https://docs.nvidia.com/cuda/wsl-user-guide/) и
[GPU reservations Docker Compose](https://docs.docker.com/compose/how-tos/gpu-support/).

## Управление

```powershell
# Автовыбор; также повторить после замены GPU/драйвера или добавления камер.
powershell -ExecutionPolicy Bypass -File .\start_vision_office.ps1

# Только CPU, без требования к NVIDIA.
powershell -ExecutionPolicy Bypass -File .\start_vision_office.ps1 -Profile cpu

# Проверить и восстановить прежний режим, не записывая новый профиль.
powershell -ExecutionPolicy Bypass -File .\start_vision_office.ps1 -CheckOnly

# Явный профиль для диагностики: при ошибке не заменяется молча на CPU.
powershell -ExecutionPolicy Bypass -File .\start_vision_office.ps1 -Profile cu124 -GpuIndex 0

# Повторный обычный запуск с уже выбранным профилем.
docker compose up -d
docker compose ps
docker compose logs --tail 100 vision-worker
```

`GpuIndex` соответствует индексу в `nvidia-smi`; автоматически используется карта 0.
WSL предоставляет устройства контейнеру, а `CUDA_VISIBLE_DEVICES` ограничивает
выбор вычислительных библиотек. Если Docker после замены оборудования вообще не
может стартовать GPU-контейнер, повторите автовыбор или явно выберите CPU.
Ошибка старта сервисов после успешного теста восстанавливает прежний профиль и
выводится оператору: она не считается успешным запуском.

## Работа и диагностика

- GPU получает только `vision-worker`. PostgreSQL, UI, API, ERP sync и каталог
  неизвестных работают на CPU; clusterer сохраняет лимит 0.5 CPU.
- YOLO сохраняет FP32 и существующий размер/частоту детекции. Число вычислительных
  CPU-потоков ограничено двумя на процесс. У ORT ограничены рабочие GPU-буферы;
  это не жёсткий лимит общей VRAM всех библиотек.
- При Python-исключении CUDA YOLO/FaceID переключаются на CPU внутри процесса.
  Повторная автоматическая попытка GPU во время работы не выполняется. После
  устранения причины перезапустите worker. Сброс YOLO меняет пространство ID
  трекера, чтобы старые ответы FaceID не подписывали новых людей.
- Нативное аварийное завершение AI-процесса обнаруживается камерой; supervisor
  перезапускает её (single-camera режим восстанавливается политикой контейнера).
  Полное зависание GPU-драйвера не гарантированно исправляется Python fallback.
- В панели производительности отображаются фактические `YOLO`, `FaceID` и причина
  CPU, а не просто список установленных ONNX providers. `CUDA unavailable`:
  проверьте драйвер/WSL; `CUDA ... failed`: смотрите ошибки библиотек/VRAM в логах.
- `out of memory`: закройте посторонние GPU-приложения, проверьте `nvidia-smi`,
  повторите проверку всех камер или выберите CPU. Не снижайте порог сходства лиц
  ради скорости. RTSP timeout/H.264 corruption нужно исправлять отдельно в сети.

## Проверки релиза

Проверено 09.09.2026 на RTX A1000 Laptop 4 GB / Windows / Docker WSL2:

- 60 тестов успешно выполнены в Windows и в отдельном Linux CPU-контейнере
  без рабочей базы/настроек. Отдельные PowerShell-тесты проверяют выбор поколений
  GPU, отсутствие NVIDIA, отказ CUDA, сохранение профиля и откат старта.
- Собраны CPU и cu124; реальные модели проверены одновременно для двух камер.
  GPU-образ без предоставленного GPU корректно выбрал CPU в тесте PyTorch.
- Живое переключение GPU -> CPU -> GPU и повторный restart worker прошли.
  После restart обе камеры подключены; YOLO/FaceID = CUDA; захват около 25 FPS,
  детекция 12–13 FPS. Модель YOLO и размер детекции 960 не изменялись.
- Последний короткий synthetic probe: CPU YOLO 247–276 мс / FaceID около 615 мс;
  CUDA YOLO 37–38 мс / FaceID около 32 мс (медианы пяти повторов).
  Это диагностические измерения на пустом кадре при фоновой нагрузке,
  не обещание постоянного FPS или точности на людях.

`cu128` задан по официальным совместимым версиям, выбор профиля покрыт тестом;
сборка и аппаратное выполнение этого профиля на Blackwell здесь не проверялись.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests
powershell -NoProfile -ExecutionPolicy Bypass -File .\tests\test_runtime_launcher.ps1
```

Далее на целевом ПК: запустить `-CheckOnly`, проверить реальный запуск и restart,
обе камеры, отсутствие роста очереди и ошибок, свободную VRAM, затем минимум
30 минут обычного и пикового потока. Короткий synthetic benchmark нельзя
интерпретировать как доступное количество дополнительных камер.

Физические GTX 1050 Ti и Blackwell не доступны на текущем тестовом ПК. Для них
обязательна проверка на месте; утверждение «100% работает на любой карте» недостоверно.
