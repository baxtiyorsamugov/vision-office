# Перенос каталога сотрудников между компьютерами

ZIP-перенос нужен для первоначального заполнения PostgreSQL нового устройства
того же учебного центра. Это снимок каталога, а не резервная копия всей системы
и не синхронизация двух компьютеров между собой.

## Что переносится

- ERP ID, ФИО, тип, активность и время обновления сотрудников.
- Сохранённые основные и дополнительные фотографии, дополнительные статусы.
- Готовые 512-мерные embeddings FaceID; контрольные суммы используемых моделей.

Локальные сотрудники, неизвестные посетители, посещения, outbox, настройки,
пароли и API-ключи не включаются. ZIP не делает запросов в ERP. Фотографии
нормализуются в JPEG без EXIF. Подписанные URL с query-параметрами не переносятся.

## На исходном компьютере

1. Откройте «Сотрудники» → «ERP» → «Перенос каталога» → «Экспорт».
2. Выберите сотрудников. По умолчанию выбраны все активные ERP-карточки.
3. Нажмите «Подготовить ZIP». Проверьте количество и предупреждения.
4. Нажмите «Скачать каталог» и перенесите ZIP на защищённом носителе.

Отсутствующие основные фото или embeddings показываются предупреждением:
такой профиль не следует считать полностью готовым к распознаванию.
Непригодные дополнительные шаблоны пропускаются с предупреждением.
Фото вне `data/persons` и повреждённые изображения останавливают экспорт.

## На новом компьютере

1. Установите актуальный код, модели и Docker по [USB-инструкции](../INSTALL_USB.md).
2. Настройте ERP того же центра с собственными `device_id` и `device_api_key`.
3. Откройте «Сотрудники» → «ERP» → «Перенос каталога» → «Импорт».
4. Загрузите ZIP и нажмите «Проверить архив». До подтверждения база не меняется.
5. Проверьте новые/дополняемые записи и пропущенные по лимиту дополнительные фото.
6. Подтвердите принадлежность доверенного архива тому же учебному центру.
7. Нажмите «Импортировать в PostgreSQL», затем проверьте ФИО, фото и FaceID в таблице.

Адрес ERP проверяется автоматически, но это **не доказательство совпадения
учебного центра**: несколько центров могут пользоваться одним ERP. Текущие
локальные настройки не содержат проверенного center UUID. До появления такого
контракта принадлежность архива обязательно подтверждает оператор.

Если модели отличаются, проверка остановится. Можно явно разрешить пересчёт
FaceID на CPU из фото. Нужны все основные фотографии; отсутствие лица или
фотографии отменяет подготовку без изменений БД. Пересчёт идёт последовательно
в интерфейсе, не в камерном worker; это дополнительная CPU-нагрузка, поэтому
для больших каталогов выберите время низкой нагрузки. Принудительно подключать
GPU для переноса не требуется.

## Повторный импорт и синхронизация

Идентификатором остаётся ERP ID, поэтому повторная загрузка не создаёт копий
сотрудников. Для существующей записи заполняются только отсутствующие ФИО,
фото и embeddings. Заполненные поля, активность, тип и время обновления
сохраняются. При отличающемся официальном URL старое фото и embedding из ZIP
не подставляются. Дополнительные фото объединяются по исходной контрольной
сумме; действует локальный лимит активных фото, снятые статусы не включаются обратно.

Если каталог изменился между проверкой и импортом, нужна повторная проверка.
Короткая транзакция защищает запись от одновременного изменения ERP-синхронизатором;
чтение камер продолжается. Импорт не перезапускает worker, RTSP или ERP-процессы.

Дальше каждый компьютер самостоятельно синхронизируется со своим ERP API по
существующему расписанию. Сокращённый ответ без ФИО/фото не стирает заполненные
метаданные; существующая логика обновлений и деактивации остаётся прежней.
ZIP не исправляет ограничения backend: новые сотрудники без полных данных
по-прежнему потребуют расширения `/persons/sync`, административного импорта
или нового снимка каталога. Это не автоматическая передача локальных фото
между устройствами.

## Безопасность и восстановление

- ZIP содержит персональные данные и биометрию и **не зашифрован**. Передавайте его
  только уполномоченному оператору на защищённом носителе; не загружайте в GitHub.
- Контрольные суммы обнаруживают повреждение, но не подтверждают автора архива.
  Принимайте только доверенные архивы. Сходство моделей не доказывает происхождение
  ранее полученных от ERP embeddings; исходный каталог должен быть проверен.
- Лимиты: ZIP 100 МБ, распакованный объём 150 МБ, JSON 16 МБ, фото 10 МБ / 20 Мп,
  1000 сотрудников. Для большего каталога экспортируйте отдельные группы.
- Импорт не использует `extractall`: разрешены только манифест и проверенные фото;
  посторонние пути, ссылки, повторы, некорректные векторы и хеши отклоняются.
- Фотографии записываются в `data/persons/catalog/<уникальная-папка>/`, PostgreSQL
  хранит относительные пути. Не копируйте PostgreSQL volume вручную.
- При обычной ошибке до COMMIT транзакция откатывается и её новые фото удаляются.
  Если результат COMMIT неизвестен из-за разрыва связи, фото сохраняются: проверьте
  базу и повторите проверку/импорт. Не удаляйте папку, пока не проверены ссылки БД.
- Перед импортом в заполненную установку используйте штатное резервное копирование
  PostgreSQL вместе с `data/persons` по [PostgreSQL runbook](POSTGRESQL_RUNBOOK.md).
- Автоматического удаления сотрудников после ошибочного импорта нет: сначала
  разберите ERP ID и связи с событиями. Не откатывайте рабочую базу без резервной копии.
- Закройте вкладку после переноса и удалите ненужные ZIP с обоих компьютеров и носителя.
  `data/exports` исключена из Git, Docker-контекста и стандартных кодовых архивов.

## Проверки разработчика

`tests/test_catalog_transfer.py` проверяет транзакции, повторы, конфликты,
совместимость моделей, сохранность синхронизации, пути и содержимое ZIP.
`tests/test_catalog_transfer_ui.py` проверяет экспорт, предварительный просмотр,
подтверждение и ошибки интерфейса. `tests/test_ai_runtime.py` проверяет CPU override.

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests
```

Для PostgreSQL-тестов задайте `CATALOG_TEST_DATABASE_URL` **только на отдельную
тестовую PostgreSQL**. Каждый тест создаёт и удаляет свою схему `catalog_test_*`.
Никогда не используйте производственный URL для тестов.
